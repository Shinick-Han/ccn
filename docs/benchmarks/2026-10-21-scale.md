# Large-repository scale benchmark - 2026-10-21

Scope: the days 31-50 item in
[`docs/reviews/codex-commercial-review-2026-10-21.md`](../reviews/codex-commercial-review-2026-10-21.md),
covering NFS/LSF measurement and large-repository scanning. NFS and LSF are not
available on this machine, so this report measures **ccn's own scaling on
Windows/NTFS** and states precisely which parts of the EDA-scale claim remain
unverified.

Everything here is a measurement of this host. The synthetic corpora are
deterministic and reproducible with `scripts/bench_scale.py`; no production or
customer source was read.

## Headline

Five runs per configuration (cold: five runs, each with a fresh cache). Medians.

| Files | LOC | cold (fresh cache) | warm (cache hit) | warm `--verify-cache` | `--no-cache` | `--no-ccn` |
|---:|---:|---:|---:|---:|---:|---:|
| 1,000 | 69,821 | **0.052 s** | **0.025 s** | 0.030 s | 0.041 s | 0.025 s |
| 5,000 | 351,339 | **0.178 s** | **0.084 s** | 0.100 s | 0.160 s | 0.086 s |
| 20,000 | 1,412,939 | **0.625 s** | **0.272 s** | 0.379 s | 0.563 s | 0.316 s |

| 20k metric | Value |
|---|---|
| cold throughput | 32,023 files/s, 2.26 M LOC/s |
| warm throughput | 73,659 files/s, 5.20 M LOC/s |
| peak working set (cold / warm) | 83.4 MB / 78.2 MB |
| peak working set, all configs | 85.6 MB (`cache_rewrite`) |
| cache file at 20k | 13.45 MiB (705 B/entry) |
| cache load / cache write at 20k | 42.8 ms / 23.6 ms |
| `--json` document at 20k | 23.36 MB |
| HTML report at 20k | 23,090 B, 0.251 s |

**Scaling is linear within measurement noise.** Fitted wall-time exponent between
5k and 20k (4x files) is 0.91 (cold), 0.84 (warm), 0.96 (`--verify-cache`),
0.91 (`--no-cache`), 0.94 (`--no-ccn`). Between 1k and 20k the exponent is
0.80-0.87 because fixed process/report overhead is amortised at small N. No
super-linear phase was found, and `CCN_TIMING` phase breakdowns are consistent
with a linear walk, a linear read/parse pass and a linear cache load.

No Rust change was made: the benchmark did not prove a hot spot that could be
fixed *safely and measurably* within the constraints of this task (see
[Bottlenecks and proposed fixes](#bottlenecks-and-proposed-fixes)). `src/loc.rs`,
`src/cache.rs` and `src/metrics.rs` are untouched.

The generator's "above the CCN guard" file is **9 MiB, not 5 MB**: `src/loc.rs:23`
sets `MAX_CCN_BYTES = 8 * 1024 * 1024`, so a 5 MB file would still be parsed by
the AST pass. 9 MiB is the smallest round number that actually exercises the guard.

## Methodology

Isolation and repetition:

* Every run gets a private `CCN_CACHE_DIR` under `%TEMP%\ccn-bench\runs\<tree>\caches`.
  Nothing is written inside the generated tree (an earlier iteration put the HTML
  report and cold JSON there; tokei classified the `.html` file as a source file
  and the entry counts grew by 3 - the harness now keeps all artefacts outside the
  scanned root).
* **prewarm** - one `--json --no-cache` run before anything is timed. It is
  reported separately as "first touch" because it is the only configuration where
  the Windows file cache is cold. Without it, the first timed configuration
  absorbs NTFS metadata and data-read misses and inflates the "cold" number by
  ~8x (observed: 6.17 s vs 0.63 s for the same 20k tree).
* **cold** - five runs, each with a *different* freshly created cache directory,
  `ccn <tree> --json`, stdout to NUL.
* **warm** - five runs against the cold run's cache, same command.
* **warm verify** - five runs with `--verify-cache` on the same cache.
* **no cache** - five runs with `--no-cache` (never loads or writes the cache).
* **no ccn** - five runs with `--no-ccn` (LOC walk only; by design this bypasses
  the cache, `src/loc.rs:250`).
* **ci** - five runs, `ccn <tree> --ci --no-report`, terminal text only.
* **report json** - five runs, `ccn <tree> --report-json` (metrics build + report
  serialisation; stdout to NUL).
* **html** - five runs, `ccn <tree> --ci --report <tmp>.html`; size recorded.
* **cache rewrite** - three A/B pairs: a plain warm run, then the mtime of one
  `.c` file is bumped and the scan reruns. The delta to the warm run is the cost
  of serialising and writing the whole 13.45 MiB cache. (A fully warm scan does
  not rewrite the cache - `src/loc.rs:323` compares the entry maps.)
* wall time is measured around `CreateProcess` -> process exit, so it includes
  ~15-20 ms of Windows process start.
* peak RSS is `GetProcessMemoryInfo(...).PeakWorkingSetSize` read from a handle
  opened on the child before it exits. `--engine powershell` is an independent
  `Start-Process -PassThru` implementation of the same matrix (wall clock
  comparable, ~25 ms higher on small trees from PowerShell's `Start-Process`
  overhead; its `PeakWorkingSet64` is sampled every 2 ms and can undershoot a
  short allocation spike, so it is a cross-check, not the reported figure).
* each configuration reports median, min and max. The host was shared with other
  agents; max values occasionally include external interference (visible as
  2-3x spikes: e.g. cold max 0.985 s at 20k).

Exact commands:

```powershell
# build (from the repository root; the tree on the scan path is unchanged by the
# other agent's edits, but freeze a copy so a concurrent rebuild cannot swap it)
cargo build --release --locked
Copy-Item target\release\ccn.exe "$env:TEMP\ccn-bench-bin\ccn.exe"

# generate + measure everything (1k, 5k, 20k, 20k one-dir, pathological,
# correctness checks, pathological checks), 5 runs per configuration
$w = Join-Path $env:TEMP 'ccn-bench'
python scripts/bench_scale.py --all --workdir $w `
    --binary "$env:TEMP\ccn-bench-bin\ccn.exe" `
    --runs 5 --cold-runs 5 --result "$w\results.json" --keep

# a single tree, if you only need one point
python scripts/bench_scale.py --files 5000 --out "$w\n5000" --make-only
python scripts/bench_scale.py --driver --files 5000 --out "$w\n5000" --workdir "$w"
```

Phase timings come from the existing `CCN_TIMING=1` support
(`grep -rn CCN_TIMING src` -> `src/loc.rs:295`), which prints
`cache load ... - walk N in ... - resolve in ...`. No code was added for this.

## Bottlenecks and proposed fixes

No fix was implemented. Each candidate below is either a behaviour change (out of
scope: "no behaviour/output changes") or too invasive to be "obviously safe", and
none is a large enough share of the 20k wall time to be measurable after a
refactor on a host that is already this noisy.

1. **Serial directory walk - the NFS risk.** `src/loc.rs:469`
   (`for entry in builder.build().flatten()`) is single-threaded and pays one
   `stat` per entry (ignore's `file_type()`), plus one round trip per directory.
   On NTFS this is 69 ms / 20k wide (11% of cold, 23% of warm) and 37 ms flat; on
   a team NFS mount it is the term expected to scale with latency, not CPU.
   *Proposed*: switch to `ignore::WalkParallel` (or a bounded producer/consumer
   that only parallelises `stat`, not ignore-rule evaluation), keeping the
   existing sort at `src/loc.rs:317` so output is unchanged. *Why not now*: it
   changes ignore-file evaluation and traversal semantics in a way that needs its
   own correctness suite (`.tokeignore`, `.p4ignore`, follow-links, cycles), and
   this host cannot demonstrate the NFS win.
2. **Cache load is a full JSON parse of the whole map.** `src/cache.rs:165`-`168`
   reads 13.45 MiB and deserialises 20k entries in 42.8 ms (16% of warm). Linear,
   but the per-entry cost (~705 B) and the full parse are what a 100k-file NFS
   warm scan pays before it does any work.
   *Proposed*: keep JSON as the portable format but add a header-only fast path
   (version/root/tool-version) and only fully parse entries whose fingerprint is
   requested; or a length-prefixed binary sidecar. Not implemented: it touches
   cache identity/portability, the exact area the review's P1-2 is about.
3. **Two allocations per cache hit.** `src/loc.rs:506` returns
   `(file_loc_from_entry(path, hit), Some(hit.clone()))`, and
   `file_loc_from_entry` (`src/loc.rs:600`) clones the `CcnSummary` (including its
   `Vec<FunctionCcn>`). Every warm file therefore duplicates its function list.
   *Proposed*: return the hit by reference and materialise owned records only in
   the report, or teach `FileLoc` to borrow. Measured ceiling: warm `resolve` is
   50 ms at 20k, so the realistic win is a few percent of warm - not measurable
   above this host's noise, and the signature change reaches into `metrics`/
   `report`.
4. **`--json` is a 23 MB document at 20k** (`src/main.rs:120`,
   `serde_json::to_string_pretty(&result)`): 23,362,420 B for 20k files, ~117 MB
   at 100k. Serialisation itself is cheap (0.266 s `--report-json` vs 0.272 s
   `--json`, within noise), but the artefact size is a real CI/log problem.
   *Proposed*: a `--json-summary`/`--json-compact` mode or `--top`-style trimming
   for the file list. This is an output-contract change, so it was not touched.
5. **Large-file LOC counting is single-threaded per file.** The 9.4 MB file costs
   75 ms (~125 MB/s) in tokei, ~100% of that tree's LOC phase, while its CCN pass
   is safely skipped. *Proposed*: none at the ccn layer - this is tokei's line
   counter; the actionable step is to document that a few multi-MB merged files
   set the LOC floor, and to keep the size guard.

The warm path also starts one Rayon task per candidate, and peak RSS grows
~4.2 KB/file (85.6 MB at 20k, ~430 MB at 100k). At the review's proposed 2 GiB
budget for 100k files this is comfortable; it is not a bottleneck today.

## What this proves - and what it does not

**Proves (on this host, this build):**

* Scan cost is linear from 1k to 20k files (fitted exponents 0.80-0.96 depending
  on the interval and configuration; 0.84-0.96 for the 5k->20k step). There is no
  super-linear hot spot in walk, read/parse, cache load/save or report build at
  this scale.
* Windows/NTFS throughput: 32k files/s cold, 74k files/s warm, 2.3-5.2 M LOC/s;
  85 MB peak RSS at 20k.
* The cache is correct at scale: entry count == analysed files, stable across warm
  runs, exactly -100 on deleting 100 files, exactly one entry updated on a touch.
* The 8 MiB AST guard works, large files stay LOC-counted, 200-deep nesting parses
  without failing, and every document mode stays parseable with exit 0.
* Directory breadth is cheap on NTFS (200 dirs vs 1: +26 ms walk).

**Does not prove:**

* **No NFS.** There is no NFS server here. The single most latency-sensitive
  phase - the serial walk with a metadata call per entry - was measured only on
  local NTFS (~3.2 us per entry). At 1 ms per NFS metadata operation, 100k files
  would add ~100 s *serially* to the walk alone, which would blow the review's
  proposed warm p95 <= 10 s. This is a prediction, not a measurement, and it is the
  first thing to test on the nominated mount.
* **No LSF.** Nothing about job scheduling, cgroup limits, shared-filesystem
  contention, CPU quota, or multiple concurrent scanners is tested.
* **No Perforce sync / P4 baseline.** `p4` is not on this machine; no depot read,
  `--baseline`, `--since`, or `--hotspots` path was exercised. The trees are not
  Git repositories either, so churn/baseline/delta costs are absent from every
  number here. A 1%-changed delta run (the review's <=30 s target) is unmeasured.
* **Windows file cache.** Every timed "cold" scan has a warm OS file cache: the
  prewarm row shows the same work at 5.16 s (20k) vs 0.625 s, i.e. first touch is
  ~8x slower. On a cold NFS client (or after a sync) expect the prewarm-shaped
  number, not the cold-cache one.
* **Synthetic corpus.** Uniform 20-120-line files, no vendor trees, no minified
  bundles, no 30k-line headers, no macro-heavy EDA C++. Real EDA sources shift
  the AST/LOC ratio and the per-file cost distribution.
* **One machine, one run set, shared host.** Another agent was building in the
  same checkout; max columns show 2-3x spikes. Medians are stable across
  repeated full runs (20k warm 0.266-0.283 s), but p95/p99 latency and
  multi-tenant behaviour are not measured.
* **HTML/CI render timings** come from a build with another agent's uncommitted
  `html.rs`/`terminal.rs` edits (scan path identical to `730e235`).

## Recommended next steps for EDA scale (100k files, NFS, P4)

Concrete, in order, with thresholds derived from these numbers:

1. **Nail down the nominated host + mount first.** Record server, mount options,
   `stat` latency (`Measure-Command { Get-Item ... }` over a sample), and repeat
   this exact harness with `--workdir` on local disk and the tree on NFS.
   *Pass*: 100k warm p95 <= 10 s, cold <= 60 s, peak RSS <= 2 GiB, cache file
   <= 100 MB. *If warm > 10 s*: compare the `CCN_TIMING` walk line against the
   NTFS 69 ms/20k baseline. If walk is > 50% of wall time, parallelise the walk
   (`WalkParallel`) - that is the single highest-leverage change and it is
   currently abandoned for lack of an NFS measurement, not because it looked
   unpromising.
2. **Measure a 1%-changed delta.** Needs a P4 workspace (`p4 sync` + touch ~1% of
   files) and `--since opened`, plus a Git equivalent for the open-source path.
   *Pass*: <= 30 s for 100k files with 1k changed, and <= 2 s for a fully warm
   unchanged tree. Today `--since` still walks the whole tree and filters
   (`src/loc.rs:280`), so the expectation is that it does **not** meet 30 s on
   NFS until the walk is parallel or the VCS file list replaces the walk.
3. **Bound the resource envelope explicitly** (the review's P1-3 acceptance):
   add a documented `--jobs`/`RAYON_NUM_THREADS` note and a scan deadline; record
   that 100k files ~ 430 MB RSS and ~67 MB cache on this build, and gate CI on
   those numbers.
4. **Re-run with `--verify-cache` as the gate mode.** It costs +39% wall on warm
   scans (0.379 s vs 0.272 s at 20k) and is the mode that survives the
   restored-mtime probe; budget for it rather than treating it as free.
5. **Keep `--report-json` (or a future summarised JSON) for CI output.** `--json`
   is 23.4 MB at 20k, ~117 MB at 100k; it is the wrong artefact for a gate log and
   its size, not its CPU cost, is the problem.
6. **Pathological corpus on the real tree**: add a >8 MiB generated file to the
   100k corpus before signing off - one such file already costs 75 ms of LOC time,
   and EDA trees often contain several.
7. **Symlink follow at scale remains untested here.** Either enable Developer Mode
   / `SeCreateSymbolicLinkPrivilege` on a test host, or run the check on Linux,
   before relying on "symlinked sources are measured".

## Reproducing and cleanup

`python scripts/bench_scale.py --help` lists every knob (`--files`, `--one-dir`,
`--pathological`, `--no-links`, `--seed`, `--driver`, `--all`, `--runs`,
`--cold-runs`, `--binary`, `--engine python|powershell`, `--result`).

All generated trees, caches, JSON captures and HTML files live under
`%TEMP%\ccn-bench` (and the frozen binary under `%TEMP%\ccn-bench-bin`); nothing is
written into the repository or into `target/`. The raw `results.json` behind the
tables above is a ~23 MB artefact of the run; it was used to write this document
and then deleted with the rest of the scratch space. Keep the scripts and this
document; delete the scratch directories with:

```powershell
Remove-Item -Recurse -Force "$env:TEMP\ccn-bench", "$env:TEMP\ccn-bench-bin"
```
